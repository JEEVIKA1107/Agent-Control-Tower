# Agent Control Tower – Evaluator & Demo Guide

This guide walks operators, evaluators, and system architects through demonstrating the 5 end-to-end scenarios in **Agent Control Tower**.

---

## Preparation & Access

1. Ensure the platform is running:
   ```bash
   npm run dev
   ```
2. Navigate to **`http://localhost:5173`** in your browser.
3. Login using one of the pre-seeded accounts (click the quick-login pills):
   - **Admin**: `admin@controltower.io` / `Admin123!` (for full access, including tampering demo and reset)
   - **Operator**: `operator@controltower.io` / `Operator123!` (for anomaly detection, approvals, and scenario execution)
   - **Viewer**: `viewer@controltower.io` / `Viewer123!` (to demonstrate RBAC permission gates)

4. Open the **"Demo Scenarios"** quick launcher by clicking the button in the topbar header.

---

## Scenario A: Normal Agent Execution Workflow

### Objective
Demonstrate telemetry ingestion, live metric updates, execution lineage graph generation, and estimated cost tracking under normal conditions.

### Demonstration Steps
1. In the **Demo Scenarios** modal, locate **Scenario A: Normal Agent Execution** and click **Run Scenario**.
   *(Alternative via CLI: `curl -X POST http://localhost:5000/api/demo/scenario-a -H "Authorization: Bearer <token>" -H "Content-Type: application/json"`)*
2. Observe the execution response showing 3 spans ingested (`triage_inquiry`, `fetch_kb_context`, `synthesize_response`).
3. Click **View in Telemetry & Lineage** or navigate to **Execution Lineage** in the left sidebar.
4. Select the newly generated trace from the trace picker dropdown.
5. **Inspect the DAG Canvas**:
   - Observe the 3 connected nodes rendered in hierarchy: Root Triage Node $\rightarrow$ Knowledge Retrieval & Response Synthesis children.
   - Note the status is green (`Completed`), with duration and token counts displayed on the node cards.
   - Click any node to open the side drawer showing call signatures and payload details.
6. Navigate to **Overview Dashboard**:
   - Confirm that total token counts and estimated token costs have updated dynamically from MongoDB aggregation queries.
   - Note the clear label: **"Estimated Token Cost ($0.002 / 1K tokens)"**.

## Scenario B: Repeated Execution Anomaly (Infinite Call Loop)

### Objective
Demonstrate real-time detection of recursive loop anomalies, severity assignment, evidence storage, and automatic circuit breaker governance recommendation.

### Demonstration Steps
1. In the **Demo Scenarios** modal, click **Run Scenario** under **Scenario B: Repeated Execution Anomaly**.
2. The server emits 4 successive spans with identical call signature (`agent-sql-generator-03:retry_query_schema:loop`), exceeding the configured recursion threshold of 3.
3. Navigate to **Anomaly Detection** in the sidebar:
   - Observe the new **Critical** anomaly row: `repeated_execution`.
   - Click the anomaly to inspect the evidence drawer:
     - **Call Signature**: `agent-sql-generator-03:retry_query_schema:loop`
     - **Repeat Count**: `4`
     - **Configured Threshold**: `3`
     - **Recommended Action**: `circuit_breaker`
4. Click **Acknowledge Anomaly** as an Operator to record operational acknowledgement.
5. Navigate to **Governance Centre**:
   - View the active recommendation generated by the governance engine: **"Immediate circuit-breaker activation to halt further downstream calls"**.

## Scenario C: Token Surge Violation

### Objective
Demonstrate detection of runaway prompt/completion token usage exceeding the governance budget ceiling, and generation of a token throttling recommendation.

### Demonstration Steps
1. In the **Demo Scenarios** modal, click **Run Scenario** under **Scenario C: Token Surge Violation**.
2. A single execution span consuming 78,500 tokens is ingested, exceeding the global policy budget of 50,000 tokens.
3. Navigate to **Anomaly Detection**:
   - Observe the **High** severity anomaly: `token_surge`.
   - Inspect the evidence drawer showing: `tokensUsed: 78,500`, `maxBudget: 50,000`.
4. Navigate to **Governance Centre**:
   - View the generated recommendation: **"Recommend throttling prompt context to 2,048 tokens and enforcing completion ceilings"**.
   - Note the linked pending **Approval Request** generated in the approval queue.

## Scenario D: Human-in-the-Loop (HITL) Approval Workflow

### Objective
Demonstrate human governance review, showing operator approval and rejection decisions, and verifying the strict architectural decoupling where actions are recorded as `simulated` or `not_executed`.

### Demonstration Steps
1. Navigate to **Human Approval** in the sidebar.
2. Select an active pending request (e.g. for `circuit_breaker`):
   - Review anomaly evidence, affected agent, and proposed action parameters.
   - Enter operator commentary: *"Approved circuit-breaker isolation. Agent runtime isolated."*
   - Click **Approve Action**.
3. Select another pending request (e.g. for `token_throttle`):
   - Enter operator commentary: *"Rejected: Temporary batch load approved by data team."*
   - Click **Reject Action**.
4. Scroll down to the **Action Execution Ledger**:
   - Confirm that the approved request produced an `ActionExecution` with status **`simulated`**.
   - Confirm that the rejected request produced an `ActionExecution` with status **`not_executed`**.
   - **Architectural Honesty Check**: The UI clearly states that external actions are simulated and have not been executed on external production agents.

## Scenario E: Cryptographic Audit Trail & Tamper Verification

### Objective
Demonstrate the integrity of the SHA-256 hash-chained audit ledger, run the controlled admin tampering simulator, identify the exact broken sequence number, and restore cryptographic validity.

### Demonstration Steps
1. Navigate to **Audit Logs** in the sidebar.
2. Click **Verify Chain Integrity**:
   - Observe the green status banner: **"Cryptographic Ledger Integrity: 100% Verified"**.
   - Review total records verified and the latest block tip hash.
3. Scroll down to the **Demonstration: Cryptographic Tampering Simulator**:
   - Select a target simulated sequence number (e.g. `#7`).
   - Click **Simulate Unauthorized Modification**.
   - The server modifies the payload of the selected simulated record without recomputing its hash.
4. Observe the verification banner update immediately to **"Tampering Alert: Cryptographic Chain Broken!"**:
   - **Broken Sequence**: `#7`
   - **Violation Reason**: *"Data integrity violation: Record content was modified after hash creation."*
   - **Diff Preview**: Displays the injected payload and compares `expectedHash` vs `actualHash`.
5. Click **Restore & Recompute Chain**:
   - The original payload is restored and cryptographic hashes are recalculated.
   - The chain returns to **"100% Verified"** status.
6. **Security Boundary Review**:
   - Review the disclosure box explaining that hash chaining provides tamper-evident integrity inside the database, but does not prevent an adversary with superuser access from re-hashing the full chain unless anchored to external WORM storage.

## Safe Demo State Reset

To restore the system back to its initial genesis state at any time:
1. In the **Settings** page or **Demo Scenarios** modal, click **Reset Demo State**.
2. Confirm the prompt.
3. All simulated records will be refreshed and re-seeded. Any genuine live telemetry or custom registered agents will remain intact.
